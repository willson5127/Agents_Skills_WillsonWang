# 需求整理

將使用者提供的筆記整理成可供開發者討論與實作的規格，使用繁體中文，除非使用者指定其他語言。

## 輸入

讀取使用者訊息或指定的文字檔案。若沒有提供任何需求內容，請使用者提供功能目標或筆記。

## 處理方式

1. 找出使用者、要解決的問題與預期成果。
2. 區分已確認需求、合理假設與待釐清問題。不要把推測寫成已確認需求。
3. 將需求改寫成可觀察的行為；驗收條件應描述操作與結果，避免只寫「正常運作」。
4. 保留原始限制，例如裝置、時程、使用者角色與資料保存要求。未提供的數字或技術選型不要自行確定。
5. 資訊不足但仍可整理時，先產出草稿並列出問題；只有缺少核心目標而無法整理時才先詢問。

## 輸出

使用下列結構，可依需求大小縮短內容：

```markdown
# 功能需求：功能名稱

## 目標與使用者
說明誰遇到什麼問題，以及期望的結果。

## 已確認需求
- 需求內容。

## 驗收條件
- 當使用者執行某操作時，系統呈現可觀察的結果。

## 假設
- 尚未確認的推定；沒有時寫「無」。

## 待釐清問題
- 會影響實作或驗收的問題；沒有時寫「無」。
```

若使用者要求存檔，依其指定路徑輸出；未指定存檔時直接在對話提供。完成前檢查每個已確認需求是否能追溯到輸入，以及驗收條件是否涵蓋主要需求。
